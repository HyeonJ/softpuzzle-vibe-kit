# 프론트엔드 품질 기준

이 문서는 Frontend agent가 퍼블리싱과 프론트 앱 개발을 수행할 때 공통으로 따르는 품질 기준입니다.

`publishing` 스킬은 디자인 반영, 반응형, 접근성, 디자인 토큰, 품질 게이트를 중심으로 이 기준을 참조합니다. `frontend-development` 스킬은 라우팅, 상태 관리, API 연동, 폼, 권한, 테스트를 중심으로 이 기준을 참조합니다.

## 디자인 반영 기준

- Figma, 화면정의서, 디자인 메모의 핵심 구조를 반영합니다.
- 디자인 토큰이 있는 경우 색상, 간격, 타이포그래피는 토큰을 우선 사용합니다.
- 임의 색상, 임의 간격, 임의 그림자, 임의 radius를 남발하지 않습니다.
- 디자인 시스템 컴포넌트가 있으면 새로 만들기 전에 먼저 재사용 가능성을 확인합니다.
- 디자인과 다르게 구현한 부분은 이유와 함께 기록합니다.

## 반응형 기준

- 모바일, 태블릿, 데스크톱의 주요 화면 크기를 고려합니다.
- 텍스트가 버튼, 카드, 표, 패널 안에서 겹치거나 잘리지 않아야 합니다.
- 고정 형식 UI는 aspect ratio, min/max width, grid track, container constraint 등으로 안정성을 확보합니다.
- hover, active, loading 상태가 레이아웃 크기를 불필요하게 흔들지 않아야 합니다.
- breakpoint별 주요 사용자 흐름을 확인합니다.

## 접근성 기준

- 의미에 맞는 시맨틱 HTML을 사용합니다.
- 클릭 동작은 `button` 또는 `a`를 사용하고, 단순 `div onClick` 사용을 피합니다.
- 폼 입력에는 label 또는 접근 가능한 이름이 있어야 합니다.
- 이미지에는 목적에 맞는 `alt`를 제공합니다. 장식 이미지는 빈 `alt`를 사용할 수 있습니다.
- 키보드로 주요 인터랙션에 접근할 수 있어야 합니다.
- 모달, 메뉴, 탭, 드롭다운은 focus 이동과 닫기 동작을 고려합니다.
- 색상만으로 상태를 전달하지 않습니다.
- 주요 텍스트와 배경의 대비를 확인합니다.

## 화면 상태 기준

화면 또는 컴포넌트는 필요한 범위에서 아래 상태를 고려합니다.

- loading: 데이터를 불러오는 중인 상태
- empty: 표시할 데이터가 없는 상태
- success: 정상 처리 또는 저장 완료 상태
- error: 요청 실패, 검증 실패, 예외 상태
- permission denied: 권한 없음 또는 접근 제한 상태
- unavailable: 외부 시스템, 네트워크, 서비스 지연 등으로 사용할 수 없는 상태

모든 상태를 반드시 구현해야 하는 것은 아닙니다. 다만 구현하지 않는 상태는 필요 없다고 판단한 이유를 기록합니다.

## API 연동 기준

- 화면 또는 컴포넌트가 사용하는 endpoint를 명확히 기록합니다.
- 요청 파라미터, 응답 데이터, 오류 응답을 구분합니다.
- loading, success, error 상태를 화면에 반영합니다.
- 사용자에게 보여줄 오류 메시지와 내부 로그용 오류 정보를 구분합니다.
- mock API와 실제 API 사용 여부를 명확히 표시합니다.
- 재시도, 취소, 중복 요청 방지가 필요한지 검토합니다.
- API 계약이 불명확하면 임의 확정하지 말고 오픈 이슈로 남깁니다.

## 폼과 검증 기준

- 필수 입력값과 선택 입력값을 구분합니다.
- 형식 검증이 필요한 필드는 규칙을 명시합니다.
- 제출 중 중복 submit을 방지합니다.
- 서버 검증 오류를 사용자에게 이해 가능한 형태로 표시합니다.
- 제출 실패 시 사용자가 입력한 값을 가능한 한 보존합니다.
- 성공 후 이동, 초기화, 토스트, inline 메시지 등 후속 동작을 명확히 합니다.
- 접근 가능한 오류 메시지와 focus 처리를 고려합니다.

## 라우팅과 권한 기준

- route path는 IA와 화면정의서의 경로 체계와 맞아야 합니다.
- deep link로 진입했을 때 필요한 데이터 로딩과 권한 검사를 처리합니다.
- 인증이 필요한 화면은 guard 또는 redirect 정책을 명확히 합니다.
- 권한이 없는 사용자는 빈 화면이 아니라 명확한 상태를 봐야 합니다.
- 잘못된 경로, 삭제된 리소스, 접근 불가 리소스의 처리 방식을 정합니다.

## 테스트와 빌드 기준

가능한 경우 아래 검증을 실행합니다.

- lint
- typecheck
- unit test
- integration 또는 e2e test
- build
- 퍼블리싱 품질 게이트

검증 명령이 없거나 실행할 수 없으면 그 이유를 기록합니다.

## 완료 보고 기준

작업 완료 보고에는 아래 내용을 포함합니다.

- 작업 범위
- 변경 파일
- 사용한 스킬 또는 하네스
- 실행한 명령
- PASS/FAIL/SKIP 결과
- 남은 이슈
- 가정
- 다음 역할에 넘길 내용
